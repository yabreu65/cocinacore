# M5 U3 — Durable Cooking Sessions Schema Proposal

This proposal defines the additive persistence boundary required for M5 U3: a tenant-scoped, resumable guided cooking session that records step progress without changing recipes, meal plans, inventory, shopping, or consumption. It is a design artifact only. It does not create or execute SQL, add endpoints, or authorize a migration.

## Decision

**Schema design: GO for review, implementation: NOT YET AUTHORIZED.**

U3 cannot safely use `calendar_payload` or `consumption_payload` as a progress store:

- `calendar_payload` is strict structured plan data and is consumed by M4 planning and coverage code.
- `consumption_payload` is the actual-consumption ledger and is consumed by Today, coverage, shopping, and consumption APIs.
- Mixing progress with either payload would create false consumption evidence or invalidate existing plan parsing.

U3 therefore needs an additive session model with explicit row-level security, idempotent events, and optimistic concurrency. The design below is the smallest model that satisfies restart/reconnect without changing M4 semantics.

## U3 contract

### Functional outcome

An authenticated user can start or resume a guided session for one exact recipe/version attached to one confirmed meal-plan slot. The session exposes a safe preview of intended quantities and permits explicit step-progress changes. Progress is durable and reconnect-safe. No operation decrements inventory, records consumption, confirms a purchase, or mutates the recipe/version.

### Supported sources

The session must be created only from:

1. A recipe/version already attached by U2 to a confirmed plan slot; or
2. A saved recipe/version plus a confirmed compatible slot, using the same ownership checks as U2.

The command must re-read the plan, slot, recipe, and version inside the transaction. Client-supplied tenant or user identifiers are never authority.

### Lifecycle

| State       | Meaning                                                                   | Allowed transitions                |
| ----------- | ------------------------------------------------------------------------- | ---------------------------------- |
| `active`    | Session can advance or repeat the current step.                           | `paused`, `completed`, `cancelled` |
| `paused`    | Session is resumable but does not accept progress commands until resumed. | `active`, `cancelled`              |
| `completed` | All validated steps are complete.                                         | none                               |
| `cancelled` | User or safety policy stopped the session.                                | none                               |

No implicit transition occurs on page load, reconnect, timeout, or a read request. A completed or cancelled session is immutable except for audit-safe metadata that does not change its state history.

### Step contract

U3 must operate on a bounded, immutable instruction snapshot captured at session creation. Each step has a stable one-based `step_index`, a bounded title, and a bounded instruction. The snapshot is not regenerated by AI and is not read from a mutable recipe after creation.

The initial implementation may accept an existing recipe instruction as one step only if the product has not approved a structured step authoring contract. It must not pretend free text is multiple ordered steps. A later step-normalization decision can extend the snapshot format without changing the event semantics.

## Proposed relational model

The following is conceptual SQL for review. It is intentionally **not an executable migration** and must not be copied into a production database without a migration implementation, manifest update, checksum review, and disposable verification.

### `public.cooking_sessions`

```sql
create table public.cooking_sessions (
    id uuid primary key default gen_random_uuid(),
    tenant_id uuid not null,
    user_id uuid not null,
    meal_plan_id uuid not null,
    day_index integer not null check (day_index between 1 and 30),
    meal_type text not null check (meal_type in ('breakfast', 'lunch', 'dinner')),
    recipe_id uuid not null,
    recipe_version_id uuid not null,
    status text not null check (status in ('active', 'paused', 'completed', 'cancelled')),
    current_step integer not null default 1 check (current_step >= 1),
    total_steps integer not null check (total_steps >= 1),
    instruction_snapshot jsonb not null,
    source_updated_at timestamptz not null,
    source_calendar_payload_hash text not null,
    version integer not null default 1 check (version >= 1),
    started_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),
    completed_at timestamptz null,
    cancelled_at timestamptz null,
    constraint cooking_sessions_plan_fk
      foreign key (meal_plan_id) references public.user_meal_plans(id),
    constraint cooking_sessions_recipe_fk
      foreign key (recipe_id, tenant_id, user_id)
      references public.user_recipes(id, tenant_id, user_id),
    constraint cooking_sessions_version_fk
      foreign key (recipe_version_id, recipe_id, tenant_id, user_id)
      references public.user_recipe_versions(id, recipe_id, tenant_id, user_id),
    constraint cooking_sessions_plan_owner_fk
      foreign key (meal_plan_id, tenant_id, user_id)
      references public.user_meal_plans(id, tenant_id, user_id),
    constraint cooking_sessions_slot_key
      unique (id, tenant_id, user_id)
);

create unique index cooking_sessions_one_open_slot
  on public.cooking_sessions (tenant_id, user_id, meal_plan_id, day_index, meal_type)
  where status in ('active', 'paused');
```

### Key design notes

- `recipe_id` and `recipe_version_id` are references, not copied recipe content. The instruction snapshot is the immutable session evidence needed for restart/reconnect.
- `source_updated_at` and `source_calendar_payload_hash` make source drift detectable. Session creation must reject a stale or unconfirmed slot rather than silently starting from changed data.
- `version` is an optimistic concurrency counter for session state. Every accepted progress mutation increments it exactly once.
- `total_steps` is bounded by the implementation contract; it is not inferred from arbitrary client input.
- The composite foreign keys require compatible unique keys on the referenced tables. The current schema already provides `user_recipes(id, tenant_id, user_id)` and `user_recipe_versions(recipe_id, version_number)` but does **not** currently expose the exact unique key `(id, recipe_id, tenant_id, user_id)` required by the proposed version FK. The implementation must add or otherwise verify a compatible unique constraint before using that FK; do not assume PostgreSQL will accept the reference.
- The existing `user_meal_plans` table does not currently expose `(id, tenant_id, user_id)` as a unique key. The implementation must add/verify that composite key or use a validated alternative that preserves tenant ownership. A plain `meal_plan_id` FK is insufficient for the ownership invariant by itself.
- Slot uniqueness is partial because historical completed/cancelled sessions must remain auditable while only one open session may exist for a slot.
- The cancellation retention policy needs owner approval: retain rows for audit, or permit explicit deletion only if an independent audit contract is approved. Default recommendation is retain.

### `public.cooking_session_events`

```sql
create table public.cooking_session_events (
    id uuid primary key default gen_random_uuid(),
    session_id uuid not null,
    tenant_id uuid not null,
    user_id uuid not null,
    operation_type text not null check (operation_type in ('start', 'resume', 'pause', 'advance', 'complete', 'cancel')),
    previous_step integer not null check (previous_step >= 1),
    next_step integer not null check (next_step >= 1),
    previous_status text not null check (previous_status in ('active', 'paused', 'completed', 'cancelled')),
    next_status text not null check (next_status in ('active', 'paused', 'completed', 'cancelled')),
    idempotency_key text not null,
    payload_hash text not null,
    created_at timestamptz not null default now(),
    constraint cooking_session_events_session_fk
      foreign key (session_id, tenant_id, user_id)
      references public.cooking_sessions(id, tenant_id, user_id),
    constraint cooking_session_events_idempotency_key
      unique (session_id, idempotency_key)
);
```

Event payload should remain minimal. The first version needs only the operation type, state transition, step transition, idempotency key, and a hash of the validated command payload. Do not persist cookies, tokens, secrets, raw request bodies, or unnecessary recipe/ingredient data.

If the same `(session_id, idempotency_key)` is retried with the same `payload_hash`, return the original event/result without changing state. If the hash differs, return a typed idempotency conflict and make no change.

## Transaction and concurrency contract

Every write command follows this sequence in one database transaction:

1. Derive `tenant_id` and `user_id` from the authenticated server session.
2. Lock the target session with `SELECT ... FOR UPDATE` scoped by `id`, tenant, and user.
3. Validate the current status, current step, expected `version`, and command transition.
4. Check the idempotency key and payload hash.
5. Revalidate the plan owner, confirmed schedule/portions, exact recipe/version ownership, and source snapshot hash.
6. Insert the event with the unique idempotency key.
7. Update the session state and increment `version` with a guarded predicate.
8. Commit and return the resulting state and event outcome.

If any step fails, roll back both event and state. A client retry after an unknown network outcome must be safe: the idempotency key either returns the committed prior result or performs the command once.

## RLS and ownership design

Both tables must use:

```sql
alter table public.cooking_sessions enable row level security;
alter table public.cooking_sessions force row level security;
alter table public.cooking_session_events enable row level security;
alter table public.cooking_session_events force row level security;
```

The policies must require both authenticated context settings:

```sql
using (
  tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid
  and user_id = nullif(current_setting('app.user_id', true), '')::uuid
)
with check (
  tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid
  and user_id = nullif(current_setting('app.user_id', true), '')::uuid
)
```

The exact policy names and role grants must follow the existing database conventions. Repository transactions must set the context on the same connection before reading or writing, and tests must prove that a missing or mismatched context cannot read or mutate another tenant.

Events should be insert-only for application roles. Updates/deletes require a separate administrative/audit decision and are out of U3.

## API boundary to implement later

No endpoint is implemented by this proposal. The future API should expose only bounded, typed operations:

| Operation     | Required input                                                | Mutation                                       | Safe result                |
| ------------- | ------------------------------------------------------------- | ---------------------------------------------- | -------------------------- |
| Create/resume | exact plan/slot or session reference, expected source/version | create session or return existing open session | sanitized session snapshot |
| Pause/resume  | session id, expected version, idempotency key                 | event + session state                          | new state/version          |
| Advance       | session id, expected version, target step, idempotency key    | event + session state                          | new state/version          |
| Complete      | session id, expected version, idempotency key                 | final event + state                            | completed snapshot         |
| Cancel        | session id, expected version, idempotency key                 | final event + state                            | cancelled snapshot         |

No operation in U3 may call inventory movement, shopping-list mutation, recipe mutation, meal-plan consumption, external providers, or AI.

## Revalidation rules

Reject or return a typed conflict when:

- the plan no longer belongs to the authenticated tenant/user;
- the slot is no longer confirmed;
- the slot's `recipeRef` differs from the session's exact recipe/version;
- the recipe is archived or the version is inaccessible;
- the source `updated_at` or canonical payload hash changed;
- the requested step is outside `1..total_steps`;
- the status transition is invalid;
- the expected `version` is stale;
- the idempotency key is reused with a different payload hash.

These failures must not reveal whether a foreign plan, recipe, or session exists.

## Migration planning gate

The next available migration is expected to be `018`, but the implementation must re-check the ledger immediately before authoring it. The migration must:

1. Use the next trusted filename and lane declared by `manifest.json`.
2. Add the required composite unique constraints/indexes before foreign keys that depend on them.
3. Create both tables, constraints, indexes, RLS policies, and `FORCE ROW LEVEL SECURITY` in one reviewed migration.
4. Preserve the existing `001–017` ledger and trusted base.
5. Update `manifest.json` only through the repository's checksum/inventory workflow; never hand-edit checksums.
6. Verify ownership targets and object counts for tables, indexes, constraints, policies, and dependent types according to the manifest rules.
7. Run `npm run db:provision`, `npm run db:migrate`, and `npm run db:migrate:verify` only against a new disposable PostgreSQL database.
8. Test both separated migration roles and application access with RLS context.

### Rollback and production compatibility

Before any production consideration:

- confirm M4 production closure and backup/restore gates independently;
- verify the migration is additive and has no data rewrite or inventory effect;
- establish whether rollback means application rollback only or also schema rollback;
- do not drop the new tables automatically during application rollback;
- require a separately approved forward-fix or schema rollback plan if the migration is ever deployed.

The current user authorization does not cover any of these migration or production operations.

## Test plan

### Repository and transaction tests

- create a valid session from an exact confirmed slot;
- resume after a new connection/restart;
- pause and continue with valid transitions;
- duplicate event with the same payload returns the original result;
- duplicate idempotency key with a different payload returns a conflict and changes nothing;
- two concurrent commands with the same expected version produce one success and one conflict;
- two concurrent creates for the same open slot produce one session;
- invalid step sequence is rejected;
- failed event insertion rolls back session progress;
- completed/cancelled sessions reject further progress.

### Authorization and data isolation

- anonymous request rejected;
- wrong user and wrong tenant cannot read or mutate a session;
- foreign plan, slot, recipe, and version are indistinguishable from not found;
- archived recipe or inaccessible version cannot start/resume a session;
- altered plan snapshot or unconfirmed portions returns a typed conflict;
- RLS denies reads/writes without matching `app.tenant_id` and `app.user_id`.

### Non-regression and no-write evidence

- `calendar_payload` remains unchanged;
- `consumption_payload` remains unchanged;
- inventory quantities and `inventory_movements` counts remain unchanged;
- shopping rows remain unchanged;
- recipe and recipe-version rows remain unchanged;
- U1 preview still returns deterministic evidence;
- U2 selection and idempotency tests remain green.

### Disposable integration gate

The migration and repository tests must use named temporary PostgreSQL resources only. The test report must record container IDs, migration ledger result, test counts, and cleanup result without publishing credentials or private record IDs. No ordinary local stack or production connection is an acceptable test target.

## Implementation stages after approval

1. **Schema slice:** verify composite keys, implement migration 018, manifest/checksum workflow, RLS, and disposable migration tests.
2. **Repository slice:** implement create/read/transition transactions and idempotency handling with focused integration tests.
3. **API slice:** add authenticated bounded commands and sanitized errors.
4. **UI slice:** add accessible guided progress and reconnect readback; keep quantities informational only.
5. **Regression slice:** run U1/U2 tests, static checks, build, disposable E2E, and no-write assertions.

No stage should begin until the preceding stage has a reviewable result. U4 actual-use reconciliation is explicitly out of scope.
