# M3.3 — Cocina autónoma del hogar: diseño U0

**Estado: diseño para revisión del PM; U0 no se declara cerrado.** Este documento presenta hallazgos estáticos del commit `e6f62548c5955a37e0c57a7b2d17468909c77457`, un diseño recomendado y decisiones explícitas. No autoriza U1, cambios de aplicación, migraciones ni operaciones de producción.

## 1. Lectura rápida

CocinaCore ya dispone de piezas reutilizables relevantes: Today contextual con filtro/ranking, perfiles culinarios, recetas persistentes versionadas, planes estructurados, proyección cuantitativa de compras, transferencia de compras al inventario y confirmación idempotente del consumo de comidas planificadas. No existe todavía un recorrido único que lleve una receta guardada desde recomendación hasta planificación, preparación guiada y reconciliación del consumo real.

**Recomendación:** extraer/reutilizar las reglas existentes detrás de un servicio de dominio determinista dentro del backend Next.js. La IA puede proponer candidatos, pero no decide si una receta incumple restricciones, si alcanza el inventario ni si se debe escribir. Toda escritura debe ser un comando separado, autenticado, confirmado por la persona y seguro ante reintentos.

**Hallazgo de gobernanza:** los issues #10 y #13 siguen abiertos y las actas de M2/M3.1 declaran aceptación funcional de producción condicional. #10 conserva pendientes de PR/CI, revisión e integración; #13 cubre remediación M2 Today/RAG/migración 014. El acta de M2 pide resolver sus seguimientos bajo el gate del PM antes de comenzar M3. M3.2 U5/U6 tiene acta de cierre; eso no cierra estos issues ni convierte producción en aceptación funcional integral.

| Necesidad | Capacidad actual | Resultado |

### Necesidad de migración

**No se puede declarar una migración obligatoria para el alcance mínimo hasta que el PM decida cómo se incorpora una receta individual al calendario y qué significa “consumo real”.** Reusar slots ya existentes, estructura `calendar_payload`, `consumption_payload` y movimientos puede permitir un flujo inicial sin migrar, pero requiere escrituras transaccionales y contrato revisado. Si se requiere una comida independiente de un menú completo, progreso durable de sesión, versionado de la instancia cocinada, o correcciones auditables/idempotentes, proponer esquema aditivo dedicado (por ejemplo, meal/cooking instance + operation key/adjustment event), migration test y RLS antes de U4. No cambiar esquema en U0 ni reutilizar JSON para ocultar una nueva semántica.

## 4. Arquitectura recomendada del motor

### Camino determinista recomendado

```text
Auth + tenant
  → bounded read snapshot (profile/restrictions, inventory+as-of, current plan, saved recipes/history)
  → normalize recipe requirements (known | unknown, never guess)
  → hard safety filter (registered restrictions first)
  → compare quantities/units (sufficient | partial | missing | unknown)
  → deterministic lexicographic ranking
  → response with provenance, freshness and reasons
  → user chooses recipe (read-only)
  → explicit command(s): plan; optionally shopping; cook/confirm consumption
```

1. **Reusar sin duplicar:** reutilizar `buildTodayContext`, `rankOneSlotOptions`, profile mapping, `compareRecipeRequirementsToInventory`/meal-plan projection, `listPersistentRecipes` y read de meal plan. Extraer composición a servicio de dominio si hoy la ruta se acopla demasiado a Gemini; mantener Next.js como único backend, no desplegar un microservicio nuevo.
2. **Restricciones primero:** cualquier alergia/hard-avoid registrada descalifica; si el candidato o sus ingredientes no se pueden normalizar, marcar no verificado y no elevarlo como seguro. Las preferencias suaves ordenan, no relajan restricciones.
3. **Disponibilidad:** calcular sólo ingredientes y unidades comparables. Estados de cada ingrediente y receta: sufficient, partial, missing, unknown; registrar `asOf` del snapshot. No afirmar “tenés todo” si hay unknown/measurement mismatch.
4. **Planificación:** si coincide con plan existente, marcarlo como “ya planificado” y pedir confirmación sólo para modificar/seleccionar slot. Evitar deducir “hoy” del último plan; la fecha/slot debe ser explícita.
5. **Ranking:** usar orden lexicográfico no suma ponderada: primero elegible por restricciones; luego mayor suficiencia conocida; luego coincidencia con plan; después tiempo estimado; luego preferencias; finalmente guardadas/historial. Presentar alternativas cuando falta información. La lista nunca altera estado.
6. **IA opcional:** utilizar sólo para ampliar candidatos o explicar alternativas después de las comprobaciones locales, con timeout/límite y protección de datos existente. Validar esquema y volver a ejecutar todos los filtros deterministicamente. Fallo de Gemini => recomendaciones locales si hay datos seguros; si no, estado vacío/no disponible y explicación. IA nunca escribe plan/compras/inventario ni declara unidades/disponibilidad verificadas.

### Semántica de datos faltantes

- **Inventario vacío:** comunicar “Todavía no hay ingredientes registrados” / “No pudimos comprobar disponibilidad”; no equipararlo a despensa físicamente vacía.
- **Inventario desactualizado:** hasta que haya freshness marker acordado, mostrar fecha/estado no verificado y permitir ver recetas, pero no afirmar suficiencia; solicitar revisión manual de disponibilidad.
- **Cantidad/unidad desconocida o incompatible:** estado `unknown`/“revisar”; no hacer auto-shopping ni auto-decrement por esa línea.
- **Perfil incompleto:** mostrar que preferencias/restricciones faltan; no inventarlas. Nunca presentar falta de perfil como certificación de inocuidad.
- **Proveedor caído:** usar candidatos locales ya validados; sin candidatos, mostrar retry read-only y no persistir fallos.

### Contratos propuestos (no implementados)

- **Recommendation read:** identidad y tenant del servidor; preferencias de filtro opcionales acotadas; devuelve candidate recipe (id/version o ephemeral), porciones, tiempo estimado si existe, ingredients, disponibilidad por ingrediente, `asOf`, provenance, warnings y estado local/degraded. Sin side effects. No se acuerda aquí un path HTTP definitivo; reutilizar `POST /api/today` sólo después de comprobar compatibilidad de slot y response contract.
- **Plan selection command:** requiere recipe/version, date, meal slot, portions e idempotency key; backend re-lee recipe+plan, valida conflictos/tenant y persiste sólo tras confirmación. Debe responder `created|already_applied|conflict` con identidad durable. Path y policy de reemplazo son decisiones PM.
- **Shopping command:** mantener la separación existente cálculo GET/POST confirm. Recalcular faltantes justo al confirmar; aceptar sólo selección server-recognized; mostrar already-present/ignored; no dupear por retry. Para candidate aún sin plan, encadenar primero plan selection confirmado o diseñar endpoint específico sin saltarse revalidación.
- **Consumption command:** derivar el snapshot de receta/version/servings server-side; permitir revisión explícita de cantidades reales según decisión PM; idempotency key/meal instance estable; revalidar y bloquear inventario, registrar movimientos y resultado en una misma transacción. Reintentar por resultado persistido; no repetir descuento si respuesta se perdió. Correcciones append-only, nunca reescritura silenciosa del movimiento.

| `plan_saving` | Disable botón, muestra operación en progreso | Comando idempotente luego de confirm |
| `planned` | Confirmación de slot guardado; acciones separadas “ver faltantes” y “empezar a cocinar” | Plan persistido |
| `shopping_review` | Compra sugerida muestra faltante, cantidad/unidad y desconocidos para revisión; selecciona uno o varios | GET lectura |
| `shopping_confirmation` | Resume cantidades elegidas; confirma agregar a compras | POST sólo tras confirmar; duplicate report/readback |
| `shopping_added` | Elementos agregados / ya presentes; link lista de compras | Shopping rows persistidos |
| `cooking` | Instrucciones exactas; avanza/retrocede pasos cuando estructura existente permita hacerlo, o lee texto íntegro sin inventar pasos | Progreso sólo local hasta decisión de persistencia |
| `consumption_review` | Revisa cantidad prevista y actual; diferencias/missing/unidades incompatibles antes de confirmar | Ninguna antes de confirmar |
| `consumption_saving` | Se confirma “Terminé y consumí”; botón deshabilitado; cliente reintenta con misma clave | POST transaccional/idempotente |
| `complete` | Cantidades descontadas y movimientos; omitidos/desconocidos enumerados con causa y opción de corregir según alcance aprobado | Consumo persistido una vez |
| `conflict` | Plan/ingrediente cambió desde lectura; muestra estado actualizado y pide nueva confirmación, no overwrite silencioso | Sin write conflictual |
| `error_recoverable` | Error de red/provider; conservar borrador local y ofrecer reconsultar estado antes de retry | GET de readback, retry seguro sólo con mismo idempotency key |

**Confirmaciones distintas:** elegir/ver receta no escribe. Guardar en planificación requiere confirmación específica. Agregar compras requiere revisar la lista de faltantes y otra confirmación. Marcar como cocinada/consumida confirma consumo; nunca se deriva de abrir la pantalla o completar una instrucción. Compra→inventario requiere su estado “purchased” y transferencia confirmada del flujo existente.

**Responsive/accessibility:** reutilizar superficies `/app/today`, `/recipes` y `/meal-planner`; cards apiladas en móvil, detalle en full-screen, desktop en master-detail; controles con foco visible, labels/unidades explícitas, estados `aria-live`, confirm buttons con nombre descriptivo. Sin pantallas nuevas en U0.

## 6. Riesgos y controles

| Riesgo | Evidencia/impacto | Control/aceptación propuesta |
|---|---|---|
| Escritura por consulta/selección | Today puede llamar Gemini en una lectura; plan POST crea plan; selección debe permanecer no-mutante. | Test de contrato/side effect: GET/recommend/abrir receta no ejecuta create/update; comparar persistencia y movimientos antes/después. Confirmación explícita por cada comando. |
| Alergia/restricción omitida | Prompt IA no es barrera; alergia debe ser filtro duro y local. | Backend revalida antes de responder y antes de ejecutar comando. No permitir “override” de allergy desde texto/modelo; desconocido => review/omit. |
| Cantidad/unidad falsa | Recipe string y inventory string; plan unit nullable; conversion limitada. | Preservar source value; parser bounded, conversión dimensional permitida sólo por tabla; status unknown para incongruencia; no default a 0/unidad. |
| Inventario stale/empty | No se observó last verified/completeness marker global. | No convertir ausencia a cero. Acordar freshness metadata o usar unknown warning. Releer justo antes de shopping/consume. |
| Decremento concurrente/doble | Inventario puede cambiar entre recommendation y confirm. | Mantener transaction + row locks del consumidor; validar cantidades actualizadas; idempotency por operación persistida; la respuesta de retry debe volver a leer resultado. Tests con dos confirmaciones concurrentes y retry post-timeout. |
| Falta/corrección de cantidad | Consumo actual consume quantities del plan y registra skips; no acepta actualizaciones/correcciones. | PM define cantidad real editable. | IA timeout/garbage | Gemini puede fallar o producir cantidades/ingredientes erróneos. | Timeout, schema validation, rate limits, safe fallback local. Revalidación no generativa. Ninguna side-effect en provider path. |
| Cocina parcial/skipped | Consumo transaccional registra skips sin dejar de confirmar meal. | Antes de confirmar enseñar líneas omitidas; después permitir revisar causa. Incluir aceptación de porciones, sobrantes y desperdicio como decisión de producto. |

## 8. Decisions for PM before U1

1. **M2 gate:** ¿Cómo se resuelven #10 (PR/CI, revisión e integración pendientes) y #13, y qué evidencia exacta cierra las condiciones funcionales M2? El acta sigue condicional; el cierre M3.2 no es waiver. Revisar también si #3 identity DB o #39 signup afecta decisiones de auth, sin ampliar U0 a esos fixes.
2. **Planning:** When the user selects a recipe, must it occupy a chosen date/meal slot in an existing plan, replace a meal, or create a standalone planned meal? What should happen if no plan/slot exists or it is concurrently edited?
3. **Inventory ownership/freshness:** Is inventory a shared household resource for all members in a tenant or personal by `user_id`? What makes it “current/complete” enough to claim sufficient?
4. **Consumption:** Should “consumo real” accept per-ingredient edits (including unused/extra/waste), or confirm the planned amount? What correction flow is allowed after an idempotent confirmation?
5. **Guided cooking:** Are the persisted free-text instructions enough for a first release, or must they be authored/normalized into ordered steps? Should step progress survive closing/reconnecting?
6. **AI/privacy/cost:** May recommendation reads send bounded recipe/profile/inventory context to Gemini whenever configured (as Today currently may), or should AI use be opt-in/limited to explicit “buscar alternativas” action?
