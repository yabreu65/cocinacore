# RLS 020 gate: unresolved candidate matrix

**NO-GO for activation or a definitive matrix.** This is a review checklist, not deployed policy. The auth bootstrap boundary, global writer, metrics guard and legacy consumers require resolution and PostgreSQL tests before implementing 020. Column grants are not row isolation. Transaction-local settings alone do not authenticate an arbitrary SQL caller.

## Candidate data policies

`T` means a valid transaction-local `app.tenant_id`, `U` a valid `app.user_id`, with an independently established authorization relationship. `tenant` means the row tenant equals T; `own` also means row user equals U. Missing, malformed, mismatched or unauthorized context must return no rows or reject writes. Runtime means `cocinacore_runtime_rls`; M means the NOLOGIN metrics view owner. These are intended rules, not current PostgreSQL behavior.

## Other boundaries

- `sessions` and `password_reset_tokens`: auth capability only; no runtime grants. Auth's pre-tenant flow and recovery need explicit safe policies before FORCE RLS. Do not use runtime or owner metrics to bypass them.
- `global_books` and `global_pdf_library`: runtime reads shared global data. 020D3 removes runtime INSERT from the candidate provisioner; only dormant global-writer views retain write capability. `global_pdf_library.uploaded_by` is a user reference; the application obtains it from the verified owner session; SQL verifies the referenced user exists but not owner status. The dedicated writer URL/flag must remain disabled until its own FORCE RLS gate passes.
- `culinary_dimensions` and `culinary_terms`: shared catalogs, not tenant-private rows. `platform_owners` requires explicit owner authorization design; `premium_review_reports` needs metrics access without exposing reports to the metrics login.
- `recipe_ai_ratings`, `premium_recipes`, `saved_premium_recipes`, `premium_recipe_reviews`, `user_meal_plan_inventory_suggestions`, and `user_meal_plan_optimization_snapshots`: no SQL HTTP consumers recorded in the runtime provisioner; verify process consumers and deny access unless a reviewed need exists.
- Nine existing RLS tables (`user_recipes`, `user_recipe_versions`, `cooking_sessions`, `cooking_session_events`, and five `real_consumption_*`/claim tables) retain their existing policies and require regression tests.

## Owner metrics under FORCE RLS

The view executes with its NOLOGIN owner's underlying column privileges; FORCE RLS applies to that identity too. A candidate needs explicit SELECT policies scoped exclusively to `cocinacore_metrics_view_owner` on every protected aggregate input. The metrics login must retain SELECT only on the fixed seven-column view, no direct base-table access, memberships or writes. Policy role identity must not be spoofable through membership. Preserve the existing guard until a fail-closed mechanism proves every required policy and relation; checking only `relrowsecurity` cannot prove complete policy coverage. Never return partial counts.

## Required PostgreSQL gates

For every candidate table test tenant A/B and two users in one tenant, absent, malformed, mismatched and unauthorized contexts; all SELECT and granted INSERT/UPDATE/DELETE paths; cross-tenant and cross-user references; pooled COMMIT/ROLLBACK context clearing; runtime, auth and owner identities; and role escalation/direct-table denials. Verify signup, login, sessions, recovery, internal jobs, shared AI history and all nine existing protected tables. Test metrics with populated tenants and FORCE RLS both with all required policies and with each policy missing. Test global writer against private chunk insertion and direct private reads. Test direct `match_chunks` denial separately from `book_chunks` RLS.

Provision dedicated roles first in an isolated database, apply and validate the future 020 policies and guard as one coordinated candidate, then activate capabilities only after all negative and compatibility tests pass. No production activation is authorized by this document.

## Global writer candidate (2H4B)

`scripts/provision-global-writer-role.sql` creates an isolated LOGIN and a NOLOGIN view owner in explicitly authorized disposable databases. The login may insert only through three fixed views, with `CHECK OPTION` on chunks requiring `global_pdf`, null tenant/book-private fields, and a non-null global book; the foreign key checks the global parent. It has no direct base-table permissions or membership in the view owner. The application authorizes the session as platform owner before saving the file and starts the database transaction only afterward. The uploader comes from that session. A failed SQL write rolls back all three records and triggers file compensation.

The view owner is not a table owner, superuser or BYPASSRLS role. Under FORCE RLS, the candidate fails closed without appropriate policies. Before activation, 020 must add narrowly scoped policies for this view owner on `global_books`, `global_pdf_library` and `book_chunks`, retaining the view check and verifying parent visibility/foreign keys. Do not grant this policy to runtime, auth or metrics identities. 020D3 removes runtime global INSERT from the candidate grant matrix; the metrics guard is unchanged and still blocks metrics with RLS enabled.

Activation order: (1) provision and verify distinct roles in a disposable database, (2) apply reviewed 020 candidate policies and run all FORCE RLS negative/positive tests, (3) configure the dedicated writer URL and explicit feature flag, then (4) run owner authorization, rollback, RAG, auth and existing RLS acceptance tests. Never activate merely because pre-020 view tests passed.

## Candidate migration gate: blocked

No migration 020 has been authored or validated. Before 020, a restricted-runtime PostgreSQL test demonstrates that a transaction carrying tenant A/user A can read inventory rows from both A and B if it does not add an application-level filter. This is a baseline failure, not a tenant-isolation PASS; transaction-local GUCs alone do not enforce the boundary.

The official runner offers an explicit `--stop-after 019` boundary. In separated-lane mode, run `--lane migration --stop-after 019`, then `--lane migration --verify-boundary 019` to verify the exact ordered checksummed ledger without asserting complete migration. Provision the candidate SQL roles, verify their identities and privileges, then use the normal official runner to resume after a real 020 is reviewed and registered. Legacy ledgers do not store checksums: boundary verification fails closed until the trusted separated-ledger adoption process is completed. Do not fabricate ledger entries or change historical checksums. The future 020 must check required roles and privileges before changing any policies. This is not authorization to migrate production, and an end-to-end test with the actual 020 remains mandatory.

At this earlier gate checkpoint, the metrics view returned null whenever any aggregate source had RLS enabled; complete seven-metric results under FORCE RLS had not yet been proven. The global writer also failed closed under FORCE RLS without policies for its NOLOGIN view owner. The later 020D4-A section records the disposable metrics candidate validation; the global writer remains disabled and blocked. Do not apply an incomplete candidate to persistent databases.

## 020B inventory component

Candidate `scripts/rls-candidates/020b-inventory.sql` is not a migration and is not in the manifest. On PostgreSQL 16 disposable, FORCE RLS was exercised as the restricted runtime with two tenants and two members of one tenant. The candidate rejects existing policies rather than accidentally OR-composing permissive policies. Runtime must have SELECT/INSERT/DELETE on inventory, UPDATE only on the mutable business columns, and SELECT/INSERT only on movements. Tenant and creator columns cannot be updated by runtime.

Inventory SELECT/UPDATE/DELETE is shared within the authorized tenant; INSERT requires the context actor as creator. Movement SELECT is tenant-shared, INSERT requires that actor and an inventory parent in the same tenant; runtime has no UPDATE/DELETE. Membership is checked using `users.tenant_id` and `tenant_memberships`. No context denies access; malformed UUIDs raise an error. A shared SQL identity can set its own GUCs: this design relies on a trusted authenticated backend, not GUCs as independent authentication.

The disposable test covers unfiltered cross-tenant reads, shared inventory, contradictory context, CRUD, cross-tenant parents, rollback, pooled connection cleanup, concurrent shopping transfer, planned-meal consumption and idempotent retry, nine preexisting RLS tables, and M5/M6 reconciliation. Historical pre-policy leakage remains tested in the baseline suite; the candidate suite expects isolation. Existing optional unscoped repository fallbacks cannot safely be used after RLS is enabled; authenticated consumers must supply scope. The M5 planned-consumption repository still selects the actor's own inventory, a pre-existing functional behavior not changed here.

Before integration into 020: verify preexisting policy composition and role ownership, coordinate column grants with the runtime provisioner, preserve visibility of the identity/membership checks after their own RLS policies are introduced, preserve the runner-managed transaction when composing the standalone candidate statements, and rerun against the complete 020 and internal processes. This component does not authorize production or establish RLS for other tables.

## 020C identity candidate: NO-GO pending auth capability

The disposable-only `scripts/rls-candidates/020c-identity.sql` enables FORCE RLS on users, tenants and memberships. It uses a narrowly scoped NOLOGIN view owner `cocinacore_identity_probe`, with no membership or BYPASSRLS and only identity-column reads, to evaluate the active user's `users.tenant_id` and matching membership without recursive runtime policies. The runtime has SELECT on the fixed probe view, cannot assume its role or read `password_hash`, and can update only its own granted profile columns. Users with multiple memberships remain restricted to the active `users.tenant_id`; switching tenants is not implemented by this candidate. Context GUCs are assertions from the trusted backend, not independent authentication.

Real PostgreSQL tests apply 020C and 020B in the same disposable cluster. Signup, rollback on injected membership failure, login, session resolution, password reset and session revocation work before tenant context. The same tests exercise tenant boundaries, cross-tenant inventory, shared inventory, parent checks, planned consumption and transaction context cleanup.

**Blocking security finding:** the current auth role needs pre-tenant user lookup and password update. Its candidate SELECT/UPDATE policies are necessarily row-wide with the present SQL interface. Moreover, even the membership INSERT policy constrained to `role='owner'` and the user's active tenant permits the auth credential to add an owner membership to an existing user who lacks one. This was demonstrated directly in PostgreSQL. Signup authorization cannot be established from arbitrary SQL issued with that shared credential; design a narrowly scoped bootstrap/auth capability before integration. No broad runtime permissions or bypass were added to hide this issue.

The probe role and view are test-only candidates and require a dedicated, reviewed provisioning contract before a future migration: the restricted migration actor cannot CREATE ROLE. Do not silently reuse the auth or metrics identity. The standalone candidates contain no transaction wrapper; the disposable harness composes both under one psql transaction, and the future runner must likewise execute them in one transaction after provisioned-role and grant preflight. Future policies on these tables must also include a separately reviewed metrics-owner policy and fail-closed guard; metrics are not resolved in 020C. Full policy/ACL composition and all nine prior RLS tables must be revalidated together before 020 can be accepted.

## 020C1-B HTTP signup activation candidate

`COCINACORE_SIGNUP_BOOTSTRAP_ENABLED` defaults to disabled. When enabled it requires `COCINACORE_SEPARATE_AUTH_DB=true`, an `AUTH_DATABASE_URL` using the fixed `cocinacore_auth` SQL identity, and a runtime SQL principal distinct from auth.
