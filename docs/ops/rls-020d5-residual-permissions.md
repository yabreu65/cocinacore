# 020D5 residual SQL permissions inventory

## Scope and candidate status

This inventory compares all 37 application tables created by migrations 001–019 with the current SQL-role provisioners, reviewed 020B–020D4-B candidates, application SQL consumers, and the new D5 invitation boundary. `schema_migrations` is an internal migration ledger and is not an application table. D5 remains a candidate outside `db/migrations`; none of this document authorizes applying a canonical 020 or changing a persistent database.

Abbreviations: **runtime** = `cocinacore_runtime_rls`; **auth** = `cocinacore_auth`; **metrics** = `cocinacore_owner_metrics` via the fixed seven-column aggregate view; **writer** = `cocinacore_global_writer` via fixed owner-owned insert views; **bootstrap** = `cocinacore_auth` EXECUTE on `signup_new_account`, whose NOLOGIN owner performs new-account inserts. Candidate RLS predicates use transaction-local authenticated `app.tenant_id`/`app.user_id` and, where introduced by 020C, the membership identity probe.

## Auth reprovisioning contract

`scripts/provision-auth-role.sql` now recognizes only two identity states: (1) the exact pre-020 baseline with no identity RLS/probe/signup objects or support roles, where legacy auth writes may be granted; or (2) a complete FORCE-RLS identity installation with either the fixed 17-policy 020C1 contract or that contract plus the exact two D4-A metrics policies, the reviewed signup function/view owners and definitions, restricted support roles, and no auth direct INSERT privilege. Any partial/drifted state fails before GRANT/CREATE/configuration changes. In the installed secure state the provisioner clears table and column INSERT grants and grants only EXECUTE on the fixed signup function; it never restores direct inserts or offers arbitrary owner membership assignment.

The disposable harness exercises signup before and after secure auth reprovisioning, login, session resolution, password recovery, direct INSERT denial and existing-user owner-membership denial. It also fingerprints roles, schema and populated user/tenant/membership data around altered/partial-state rejection cases.

## Role and function boundary

- Runtime, auth, owner-metrics LOGIN, and global-writer LOGIN are separate NOSUPERUSER/NOBYPASSRLS roles with no role memberships or owned application objects. The signup NOLOGIN owner and identity-probe NOLOGIN owner are narrowly scoped; only the signup owner owns the signup function and only the identity probe owner owns the membership view.
- Auth has pre-tenant read access to user/tenant records by design, but secure mode revokes all direct table/column INSERTs for tenants/users/memberships. It has no runtime membership. The signup capability generates IDs and the owner membership internally.
- Owner metrics can SELECT only its fixed seven-count view. Global writer can INSERT only through fixed owner-owned views. Neither LOGIN receives direct table privileges or function execution.
- Application functions are not an implicit PUBLIC API. The runtime provisioner revokes PUBLIC and runtime execution from app functions, granting only the two profile validators needed by constraints. The auth provisioner revokes all function access before granting signup execution in secure mode. Metrics/writer provisioners likewise allowlist their view boundary. Trigger functions execute as part of table operations and are not direct runtime capabilities.
- The `pgcrypto` and `vector` extension functions may retain PostgreSQL extension-default PUBLIC EXECUTE. That does not grant table access; `match_chunks` is explicitly revoked from PUBLIC and app roles. The disposable candidate suites verify app-function and role boundaries. Review future extension additions separately.

## Residual blockers before canonical 020

1. Compose D5 and the already reviewed 020B–020D4-B candidates into the canonical 020 with exact state guards, then run the entire disposable acceptance suite against that composition. This document and its candidate are not a production gate.
2. Review `premiumBoardService`'s separate Supabase REST credential/policies and any other non-PostgreSQL application identities. The SQL inventory intentionally grants those tables no runtime SQL access; it does not establish REST isolation.
3. Decide and test the supported invitation write/acceptance capability. D5 only closes the exposed summary reader; it does not re-enable invitation creation, revocation, or acceptance.
4. Reconcile migration runner behavior, backups, rollback, operational approval and persistent-environment rollout before any migration or credential activation.
