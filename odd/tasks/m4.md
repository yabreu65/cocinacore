## Specs

### S1 — Product intent and supported domains
> DESCRIPCIÓN DE M4: convertir CocinaCore en asistente de cocina predictivo pero conservador: anticipa faltantes y desperdicios, adapta menú y propone compras, sin inventar cantidades ni ejecutar acciones irreversibles automáticamente. SOPORTE DE RUBROS: hogar primero con dominio reutilizable multi-tenant y perfiles a futuro restaurantes/panaderías/catering; no hacer supuestos del perfil, preservar diseño móvil.

### S2 — U0 audit and plan
> (U0) auditoría de código/datos/UX actual: inventory, expiry/expirationDate, lowStockThreshold, today/one-slot, meal-plan-simulation/projection/optimizer, compras e historial/consumo; identificar funcionalidades existentes y huecos, revisar amenazas, compatibilidad; registrar especificación, plan de datos y pruebas, descomposición detallada U1-U5, riesgos y contratos de calidad, sin duplicar módulos.

### S3 — U1 coverage forecast
> (U1) pronóstico determinista y explicable de cobertura de ingredientes para horizonte configurable 7/14 días basado SOLO en inventario cuantificado y plan futuro confirmado; diferencia reservado vs consumo confirmado; exactitud de unidad/porciones, no inventar consumo histórico; devolver sufficient/partial/missing/unknown y cantidades cuando comparables; límites fechas/tenant/timezones; API y tarjetas de panel.

### S4 — U2 waste prevention
> (U2) prevención de desperdicios: vencimientos reales, exclusión de ya vencidos, prioridad segura de ingredientes próximos y recetas compatibles con preferencias/evitaciones/alergias, no alucinar fecha; alertas no intrusivas y justificadas con acción del usuario.

### S5 — U3 adaptable planning
> (U3) planificación adaptable: recomendaciones basadas en tiempo/preferencias/inventario/presupuesto sólo si datos reales, explicaciones claras, cambios en modo propuesta con confirmación explícita, sin alterar planes ni descontar stock sin consentimiento ni doble conteo.

### S6 — U4 purchase suggestions
> (U4) compras anticipadas sugeridas: lista consolidada de faltantes para horizonte y porciones, unidades compatibles, no duplicar inventario comprado/traspasado ni alterar listas existentes sin confirmación, precio/costo solo si disponible y etiquetado como estimación; usuario confirma.

### S7 — U5 end-to-end quality and release
> (U5) validación integral, UX responsive y accesibilidad, seguridad tenant/auth, idempotencia, límites, errores/unknown, CI E2E aislada con PostgreSQL/Redis descartables, pruebas UI y real production acceptance sin escrituras sintéticas por defecto, cierre documental, desplegar y limpiar.

### L2 — U0 audit, data/test plan, risks, and quality contracts (2026-10-25)

**Baseline and existing modules**
- Clean baseline verified at `2a6cb3c5c8cac2bc8fe01d2e0eb5de698ee94bb5`, with `main == origin/main`; branch `feat/m4-u0-audit` is rooted at that SHA.
- Inventory quantity/unit, expiration date, and low-stock threshold fields exist at `frontend/src/lib/db/types.ts:182-198`; migration 003 owns base inventory and movement history. Inventory API routes are tenant-scoped (`frontend/src/app/api/inventory/route.ts:44-68,115-141`).
- Unit normalization/projection already handles `sufficient | partial | missing | unknown` and comparable missing amounts (`frontend/src/lib/inventory/meal-plan-projection.ts:19-35,123-154,173-195`). No existing 7/14-day coverage API/contract was found.
- Saved plans and consumption evidence exist (`frontend/src/lib/db/types.ts:260-278`; migration 012; `frontend/src/lib/db/repositories/mealPlanConsumptionRepository.ts:65-89,131-260`). Purchased-to-inventory transfer is transactional/idempotent and migration 015-backed (`frontend/src/lib/db/repositories/shoppingListRepository.ts:132-200`). Confirmed consumption evidence is separate from estimated/unknown AI history (`frontend/src/lib/today/context.ts:161-185,217-232`).
- Meal-plan projection is the closest reusable coverage logic; simulation is heuristic rather than an explicit horizon contract (`frontend/src/lib/inventory/meal-plan-simulation.ts:54-68,85-115,121-152`). `SimulationControls` says edits are temporary and invokes an explicit Apply callback (`frontend/src/components/home-os/SimulationControls.tsx:7-27`); the callback's write boundary remains unknown and must not be reused in U3 without a separate inspection.
- Date behavior mixes UTC-shaped ISO validation and local-day comparison (`frontend/src/lib/today/one-slot.ts:3-46`; `frontend/src/lib/inventory/normalize-inventory.ts:35-69`).

**U1 data plan (read-only, migration-free candidate)**
- Read only tenant-scoped, quantitatively valid inventory (`quantity`, `unit`) and already persisted future plan/recipe requirements; use the existing comparable-unit normalization/projection rather than inventing another module.
- Treat explicit persisted future plan entries as the input plan; keep temporary simulation changes out. Exclude meals with confirmed consumption evidence. Never treat AI estimates or missing data as consumption or zero stock.
- Do not persist forecasts, add user preferences, introduce tenant timezone columns, modify existing lists, or call external recommendation providers in U1. No DDL is in this plan. Any need for DDL or a non-read-only production effect stops for a separately authorized migration plan and permission.
- Define one request `asOf` day and an explicit timezone interpretation using existing persisted data; do not claim a tenant timezone where none is stored. Return unknown when a date boundary, amount, unit, plan confirmation, or comparison cannot be established safely.

**U1 test plan**
- Add one RED/GREEN behavior test per requested U1 rule: only quantified inventory and persisted future plan; reservation/consumption separation; comparable units and portions; exact statuses and quantities; 7/14-day horizon allowlist; date-boundary behavior; tenant isolation; and no writes/external provider calls.
- Exercise the public API and Today UI. Assert deterministic output, exact status/quantity behavior, and that rejected or unknown inputs do not alter inventory, meal plans, consumption, shopping lists, or counters.
- Pin existing shared projection/normalization behavior once for the directly changed helper, and differentially compare touched existing routes against the base commit in a temporary scratch copy. Use only disposable PostgreSQL/Redis for applicable integration tests; never use the original local database.
- Run focused tests, then the repository's full lint/typecheck/build/CI checks once for the U1 candidate, GGA, and native RDD assessment. No production acceptance with synthetic writes.

**Threats, compatibility, and quality contracts**
- Tenant/user confusion could leak another household's plan or inventory; each query and returned row must remain scoped to authenticated tenant (and user where the repository requires it).
- Ambiguous quantities/units, estimated recipe history, unknown consumption, expired inventory, timezone boundaries, duplicate transfers, and temporary simulations can create false confidence or double counting. Preserve `unknown`; never infer zero, sufficient, a date, or consumption.
- Forecast is deterministic, explainable, read-only and idempotent. Results for identical persisted inputs and `asOf` are identical. The API accepts only 7 or 14 days, bounds input/output, and degrades to explicit unknown rather than guessing. UI communicates evidence and uncertainty without persisting or mutating state.
- U2-U4 must reuse existing expiry, restriction, planning, list, transfer and consumption behavior where compatible; inspect exact persistence/caller boundaries before changes. Existing data/schema compatibility is mandatory; no destructive migration or list/plan rewrite.
- Focused existing test suites include inventory repository, consumption repository, projection, simulation, and Today API/context tests. No tests were run during U0 exploration.
